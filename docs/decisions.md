## 2026-09-21 — 1단계: 현황 분석

### D-01 / 내가 쓴 추정식이 어디 있는지 찾는 것부터 막혔다
- **막힌 것**: "내 코드 vs 라이브러리 코드"를 나누려 했는데, 표류각·풍경사각·속도손실 추정식이
  `src/`가 아니라 `public/vesseljs/examples/vessel_simulation.html` 안에 있었다.
  즉 **내가 쓴 물리식이 MIT 라이선스 벤더 디렉터리 안에 섞여 있다.**
- **고른 방법**: 1단계에서는 위치만 확정하고 옮기지 않는다. 2단계에서 `src/physics/`로 순수 함수 추출.
- **버린 방법**: 지금 바로 파일을 옮기는 것 — 동작 검증 기준(테스트)이 없는 상태에서 옮기면
  회귀가 났는지 알 방법이 없다. 테스트를 먼저 만들고 옮긴다.
- **확인 방법**: 추출 후 동일 입력에 대해 현재 iframe 출력과 수치가 일치하는지 대조.

### D-02 / Vessel.js를 브라우저 없이 계산에 쓸 수 있는가
- **막힌 것**: 검증하려면 값을 뽑아야 하는데, 지금 계산은 iframe 안 WebGL 씬과 한 덩어리다.
  Three.js·WebGL 없이 숫자만 뽑을 수 있는지 불확실했다.
- **고른 방법**: Node에서 `public/vesseljs/source/jsm/vessel.js`를 그대로 `import`해 보고 확인.
  → **성공.** `Ship`, `calculateStability`, `WaveCreator`, `WaveMotion`, `HullResistance` 전부 Node에서 돌았다.
  따라서 Vitest 단위 테스트에 WebGL 모킹이 필요 없다.
- **버린 방법**: puppeteer/headless Chrome로 iframe을 띄워 postMessage 값을 긁는 방식 —
  느리고, 실패 원인이 물리인지 렌더링인지 구분되지 않는다.
- **확인 방법**: `node probe.mjs` 실행으로 GMt=0.587 m, 배수량 6241 t, calmResistance 88.5 kN 취득.

### D-03 / 파고 2 m를 넘으면 부가저항이 오히려 줄어든다
- **막힌 것**: 저항 값을 파고별로 뽑아 보니 Hs=2.0 m에서 53.6 kN이던 ΔRaw가
  Hs=2.1 m에서 **17.7 kN으로 떨어지고 그 뒤로 파고와 무관하게 고정**됐다.
- **원인**: Vessel.js `HullResistance.totalResistance`가 파고 2 m 이하에서만 Kreitner 식을 쓰고,
  초과하면 `Rtadd = 1.2 × calmResistance` (정수저항 + 20% sea margin 고정)로 전환한다. 라이브러리 설계상의 분기다.
- **고른 방법(예정)**: 2단계에서 파고 2 m 초과 구간을 내 모듈에서 별도 처리하고,
  화면에는 해당 구간을 "라이브러리 적용 범위 밖 — 참고용" 으로 표시.
- **버린 방법**: 라이브러리 파일을 직접 고치는 것 — 업스트림과 갈라져 업그레이드가 불가능해진다. 어댑터에서 감싼다.
- **확인 방법**: `docs/validation.md`에 파고별 표로 불연속 지점을 그대로 기록.

### D-04 / 같은 화면에 부가저항 값이 두 개, 서로 다르다
- **막힌 것**: 하단 HUD의 ΔRaw와 3D 오버레이 LVL4의 ΔRaw가 다른 값이다.
  HUD는 `18.5·Hs²·√2.9` (출처 불명 상수), 오버레이는 Vessel.js 계산값. Hs=2 m에서 126 kN vs 53.6 kN (2.35배).
- **고른 방법(예정)**: 계산 경로를 하나로 통일(`src/physics/`), HUD는 그 결과를 표시만 한다.
- **버린 방법**: 둘 중 하나를 숨기는 것 — 어느 쪽이 맞는지 모르는 상태로 덮는 셈이다. 먼저 검증한다.
- **확인 방법**: 통일 후 두 표시값이 동일한지 단위 테스트로 고정.

### D-05 / 풍경사각이 폭풍에도 1도가 안 나온다
- **막힌 것**: IMO 기준 풍속 26 m/s를 넣어도 현재 식은 0.33°를 낸다. 직관적으로 너무 작다.
- **원인 가설**: (a) 수풍면적을 `LOA×(D−T+3)×0.6 = 221 m²`로 잡아 실제 PSV 측면적(≈370 m²)보다 작고,
  (b) 모멘트 팔을 수면 위 중심 높이(2.25 m)로만 잡아 수중 측면적 중심까지의 거리(≈7.9 m)를 쓰지 않았고,
  (c) 풍압계수가 없어 504 Pa(IMO) 대신 414 Pa로 계산된다. 합쳐서 약 7배.
- **고른 방법(예정)**: IMO IS Code 2008 기상 판정 기준(weather criterion)의 풍압 절차와 나란히 계산해
  `docs/validation.md`에 차이와 원인을 표로 남긴다.
- **버린 방법**: 계수를 임의로 키워 "그럴듯한" 값을 만드는 것 — 검증이 아니라 튜닝이다.
- **확인 방법**: 같은 입력에 대한 두 방법의 값과 비율을 문서에 명시.

## 2026-09-21 — 2단계: 구조 분리와 검증

### D-06 / physics를 어디에 둘 것인가 — iframe 안이냐 Vue 쪽이냐
- **막힌 것**: 추정식이 iframe(`public/`) 안에 있어 Vite가 처리하지 않는다.
  `src/physics/`로 옮겨도 iframe에서 import할 수가 없다.
- **고른 방법**: **계산을 전부 Vue 앱으로 올리고 iframe은 렌더러로만 남긴다.**
  Vue가 `src/physics/`로 값을 계산해 postMessage로 내려보내고, iframe은 받은 각도·변위로 그리기만 한다.
  Vessel.js는 어댑터가 런타임 동적 import(`/vesseljs/source/jsm/vessel.js`)로 불러온다.
- **버린 방법**:
  (a) iframe을 Vite 멀티페이지 엔트리로 승격 — three_r126.js 1.1 MB가 번들에 중복으로 딸려 들어간다.
  (b) Vessel.js 소스를 `src/`로 이동 — 벤더 코드와 내 코드 경계가 다시 흐려진다. 업스트림 갱신도 막힌다.
- **확인 방법**: 화면의 모든 수치가 `src/physics/` 한 경로에서 나오는지, HUD와 3D 오버레이 값이 일치하는지.

### D-07 / 두 번째 부가저항 참고 기준을 넣지 못했다
- **막힌 것**: Kreitner 외에 독립적인 비교 기준으로 ISO 15016의 STAWAVE-1을 쓰려 했으나,
  ISO 15016 본문과 ITTC 7.5-04-01-01.2 원문에서 계수를 확인하지 못했다(PDF 텍스트 추출 실패).
- **고른 방법**: **넣지 않는다.** 기억으로 계수를 적으면 검증 문서가 아니라 추측 문서가 된다.
  `docs/validation.md`의 "남은 검증"에 미완료로 명시한다.
- **버린 방법**: 대략 맞는 값을 적고 "참고"라고 쓰는 것 — 이 프로젝트가 고치려던 문제를 그대로 반복하는 셈이다.
- **확인 방법**: 없음. 미완료 항목으로 남긴다.

### D-08 / 속도손실 식은 틀리지 않았다
- **막힌 것**: 배포본의 `ΔR/(3R₀)`가 근거 없는 식인 줄 알았다.
- **확인한 것**: 정수저항 R ∝ V², 출력 일정 가정에서 `u³ + r·u − 1 = 0` (u = V/V₀)을 풀면
  r < 1 구간에서 `ΔR/(3R₀)`와 **1%p 이내로 일치**한다. 즉 식은 타당한 1차 근사였고,
  문제는 식이 아니라 **입력으로 들어가던 ΔR**(2 m 분기)이었다.
- **의미**: "내가 만든 것이 전부 틀렸다"가 아니라 어느 부분이 왜 맞고 왜 틀렸는지 구분해서 말할 수 있게 됐다.

### D-09 / 탭을 잠깐 가리기만 해도 3D 품질이 영구히 낮아졌다
- **막힌 것**: 저사양 기기 대응으로 "3초 연속 24 fps 미만이면 품질을 낮춘다"를 넣었는데,
  브라우저에서 확인해 보니 항상 `1 fps · 표준`으로 떨어져 있었다.
- **원인**: 브라우저는 탭이 가려지면 `requestAnimationFrame`을 1 Hz로 제한한다.
  그 값을 그대로 "느린 기기"로 해석해 품질을 낮추고 있었다. 사용자가 탭을 3초만 옮겨도 그렇게 된다.
- **고른 방법**: 렌더러가 `document.hidden`일 때는 fps 표본을 아예 보내지 않고,
  가시성이 바뀌면 측정 창을 새로 연다. 부모 쪽에도 **되돌림**(8초 연속 50 fps 초과 시 한 단계 복구)을 넣었다.
- **버린 방법**: 임계값을 24 → 10 fps로 낮추는 것 — 증상만 가리고 진짜 저사양 기기를 못 걸러낸다.
- **확인 방법**: 수정 후 브라우저에서 품질이 `고품질`로 유지되는 것을 확인.
  다만 개발 환경 패널이 항상 `hidden`으로 보고해 **기기별 실측 fps는 아직 못 구했다**(미측정으로 기록).

### D-10 / 해역 비교에서 3D를 두 개 띄울 것인가
- **막힌 것**: "두 해역을 나란히"를 문자 그대로 하면 WebGL 컨텍스트가 둘이 된다.
- **고른 방법**: **3D는 하나만 유지하고 비교는 수치·차트로 한다.**
  비교에서 실제로 필요한 것은 "어느 쪽이 얼마나 더 가혹한가"이고, 그건 그림보다 숫자가 정확하다.
  대신 주기 스윕 차트를 넣어 "같은 파고라도 주기가 바뀌면 순위가 뒤집힐 수 있다"를 보여준다.
- **버린 방법**: iframe 2개 — 모바일에서 프레임이 반토막 나고, 텍스처·선체 지오메트리도 두 벌이 된다.
- **확인 방법**: 비교 패널 전체 재계산 비용 측정 → 스냅샷 1회 약 10 µs, 스윕 26회 포함 1 ms 미만.

### D-11 / Vessel.js를 public에 둔 채로 앱에서 쓰는 법
- **막힌 것**: Vite는 소스에서 `public/` 파일을 import하는 것을 막는다(개발 서버가 500을 돌려준다).
- **고른 방법**: 번들러가 정적 분석할 수 없는 형태(`new Function('u','return import(u)')`)로 감싸
  브라우저가 원본 파일을 그대로 받게 한다. Node(테스트)에서는 표준 동적 import를 쓴다.
- **버린 방법**: `src/vendor/`로 복사 — 라이브러리가 두 벌이 되어 "무엇이 벤더 코드인가"가 다시 흐려지고,
  업스트림 갱신 시 iframe 쪽과 앱 쪽이 갈라질 수 있다.
- **확인 방법**: 개발 서버·프로덕션 빌드 양쪽에서 로딩 확인, 번들에 Vessel.js가 섞이지 않은 것 확인(280 KB).

### D-12 / 비교 모드에서 지도 핀이 하나로 겹쳤다
- **막힌 것**: 비교 모드를 켜면 지도에 A와 B가 같은 자리에 겹쳐 찍혔다.
  지도의 주 마커를 "지금 편집 중인 해역"에 묶어 놨는데, 편집 대상이 B로 바뀌면 A·B 둘 다 B를 가리켰다.
- **고른 방법**: 주 마커는 항상 A, 보조 마커는 항상 B로 고정하고,
  지도 클릭이 어느 쪽을 바꾸는지는 `A 지정 / B 지정` 버튼으로 **사용자가 직접 고르게** 했다.
- **버린 방법**: 클릭할 때마다 A↔B를 번갈아 바꾸는 것 — 다음 클릭이 어디에 반영될지 화면만 보고 알 수 없다.
- **확인 방법**: 브라우저에서 두 마커가 각각 다른 좌표에 표시되는 것을 확인.

### D-13 / Electron 데스크톱 패키징을 걷어냈다
- **막힌 것**: `file://`로 `dist/index.html`을 열어 절대 경로 자원(`/vesseljs/...`, 3D iframe)이 해석되지 않았다.
  확인해 보니 이번 작업 전부터 이미 동작하지 않던 상태였다.
- **고른 방법**: 제거. 결과물은 Vercel 웹앱이고, 데스크톱 패키징은 "계산을 검증한다"는 이 프로젝트의 목적에 보태는 것이 없다.
- **버린 방법**: Electron 안에 로컬 http 서버를 띄우거나 경로를 전부 상대경로로 바꾸는 것 — 브라우저에서 이미 되는 것을 다시 만드는 비용이다.
- **확인 방법**: 제거 후 빌드·테스트·lint 통과.
